摘要　通用操作系统的 CPU 调度器以线程公平份额为目标，而数据库的并发需求由事务依赖、锁临界区与提交路径等结构语义决定。两者之间的语义鸿沟在混合负载、外部干扰与突发流量下表现为尾延迟放大、优先级反转与过载崖点。既有工作（如 UFS）通过要求用户显式划分时间敏感与后台两层来缓解该问题，但在业务高频变化、AI Agent 动态生成负载的现实下，人工优先级标注既不可持续也不可行。

本文提出韧性优先（resilience-first）的调度目标：优化对象不是单场景峰值吞吐，而是服务级目标下的有效吞吐（goodput）、尾延迟、过载崖点位置与恢复时间。在此目标下，本文设计 EEVDF-Sem——一个以 EEVDF 公平思想为基座、通过 sched_ext 实现的单池调度器。它不要求任何业务标注，仅施加两类普适的结构语义微调：（1）提交早行，对 COMMIT/ROLLBACK 施加有界虚拟截止期奖励；（2）锁持有者条件性优先级继承，仅在等待边出现时让持有者继承最急等待者的虚拟截止期，继承深度与时间均有硬上限，并以借还记账保证周期级公平。配合以排队时间为信号的准入控制与突发吸收机制，系统在过载时退化而非崩溃。

基于 MySQL 9.7 的分阶段原型采用前台协程 reactor + 固定执行池 + sched_ext 桥接的混合架构：reactor 将连接等待、断连感知与 SQL parse 前置，使准入和调度在执行前获得语义；v4 设计进一步取消已不再具有客户端价值的排队工作；worker 保留 MySQL 的同步执行语义，避免将协程化误当作并发控制。初步测量表明：在外部 CPU 噪声下，语义发布使点查 p99 劣化从 7.6 倍降至 1.4–1.7 倍；热点更新负载吞吐提升 66%；代价是干净负载约 5% 的吞吐开销。断连早弃尚未纳入这些实测结果，完整评估计划见 §6.7。

1 引言

数据库管理系统（DBMS）的并发控制决定了事务间的逻辑顺序，但“可运行的事务如何获得 CPU”传统上被交给操作系统。这一分工在专用硬件与平稳负载的时代运转良好，如今却在三方面同时失效：

第一，负载形态变了。AI Agent 成为主要服务调用方后，数据库访问呈现强烈的潮汐与脉冲特征：一次任务拆解扇出数十个并行子查询，超时即程序性重试，重试过载互为正反馈。此类负载由程序动态生成，既无法预测，也无法人工标注优先级。

第二，优化的目标函数错了。工业界的基准竞赛历史表明，针对特定场景的调优往往对客户日常负载收益甚微甚至为负，却把复杂度转嫁给用户 [24]。当业务以周为单位调整时，任何“为某负载特调”的参数都必然过期。真正需要的不是最好情况下的峰值，而是最坏情况下的可预期性：突发不崩溃、越崖不雪崩、噪声下尾延迟有界。

第三，瓶颈的位置变了。随着锁与缓冲池优化日趋成熟，非业务开销的重心上移至通信、上下文切换与调度协同：近期全栈剖析显示简单事务 52%–67% 的运行时消耗在消息传递上 [28]；本仓库原型亦观测到，队列为空时仍有 33% 的执行任务因 worker 被抢占或迁移而等待 100–500µs。这意味着仅在数据库内部优化已不足够，必须打通数据库语义与内核调度。

本文的出发点是：调度器应消费结构语义而非业务标签。有些调度事实无需任何人告知系统——COMMIT 是 2PL 锁的批量释放点；锁/latch 持有者被抢占会连带放大所有等待者的延迟；等待时长本身就是紧迫度信号。这些事实普适、可自动获得、与业务无关。

据此，本文提出 EEVDF-Sem，一个以 EEVDF 虚拟时间公平性为基座、经 sched_ext/eBPF 实现的调度器，并围绕它构建完整的数据库韧性栈。本文的贡献如下：

  1. 韧性优先的目标形式化与提前越崖模型（§2.2–§2.4）：以 goodput 膝点/崖点、基线越崖行为、恢复时间与噪声下尾延迟劣化倍数为优化对象；以 G = C − S 分离服务端完成尝试与客户端有效完成，给出 S′ > C′ > 0 时 goodput 先于完成率峰值下降的可证伪条件。
  2. 主流线程池能力边界的机制化分析（§2.3、§6）：比较 MySQL/MariaDB/Percona、TiKV、CockroachDB 与代理池，将限制归纳为依赖失明、计数失真、静态尺寸与过载语义四类；区分配置、存活、busy 与 runnable，并以 N14 提供可复现验证路径。
  3. 单池公平基座上的两类结构语义微调（§4）：COMMIT/ROLLBACK 的有界虚拟截止期奖励，与锁持有者沿等待边的有界虚拟截止期继承，辅以先借后还的公平记账。
  4. 以排队时间为信号的数据库准入控制（§4.4）：区别于以线程数或队列深度为信号的做法，直接观测包含 OS 调度等待的排队时间，将膝点与崖点推远，并保证基线越崖后退化而非持续崩溃。
  5. 面向请求生命周期的混合执行边界（§3、§5.2）：前台 reactor 在 worker 之前完成连接多路复用、断连感知与 parse，使语句分类、准入和取消成为执行前决策；固定执行池保留 MySQL 的线程与阻塞语义，避免全局协程化的高风险改造。
  6. 分阶段原型与初步证据（§5–§6）：语义发布在外部噪声下将 p99 劣化从 7.6× 降至 1.4–1.7×，热点更新吞吐提升 66%，干净负载代价约 5%。

2 背景与动机

2.1 两层调度的语义鸿沟

EEVDF/CFS 将线程视为可互换的 CPU 消费者，按权重分配虚拟时间；数据库则掌握事务状态、锁等待图、提交路径与后台角色。信息的不对称是双向的：数据库的优先级队列无法保证被唤醒的 worker 立即获得 CPU；内核无法从一个普通 tid 推断它正持有数十个事务所等待的锁。Practical DB-OS Co-Design [27] 将此类问题归因于通用 POSIX 接口缺乏数据库定制支持；UFS [5] 进一步证明，即使配置 cgroup 权重，EEVDF 的唤醒放置启发式仍会使 CPU-bursty 事务扎堆至少数核，吞吐损失达 50%。

2.2 五类典型失效模式

a. 优先级反转放大。持锁者 H、等待者 W 与无关 CPU 密集任务 M 构成经典三角（图 1）：M 抢占 H，W 事实上继承 H 的低优先级。在 MySQL/InnoDB 上，该问题有两个独特形态：显式事务持有者在语句间隙不占任何线程（real_id = 0），内核侧无法定位提权对象；线程池模型下全部 worker 阻塞于行锁时，持有者的 COMMIT 在队列尾部等待无线程可用的执行池，形成执行池活性死锁——它在 InnoDB 等待图上无环，死锁检测器不可见。

b. 过载膝点与崖点。超过最优并发度后，lock thrashing [26] 与上下文切换使边际 goodput 收益下降；排队则使端到端 RT 通常比吞吐更快上升。固定大小线程池避免了线程爆炸（MySQL Thread Pool 极端情况下可达 65536 线程），却把过载转化为排队与 RT 增长，为后续超时崩塌埋下条件。过载服务器研究同样表明，响应时间增长会诱发客户端放弃，而服务器继续处理被放弃请求会造成无效功与 goodput 下降 [41]。

c. 非业务开销主导。本仓库微基准量化了三类开销的量级：notify_all 惊群造成每秒 25 万次上下文切换，吞吐仅为修复后的 1/10；每命令两次切换加 epoll 重注册的交接开销可解释廉价点查场景近八成的性能差距；外部 CPU 噪声使默认调度器下 p99 劣化 7.6 倍。

d. 客户端超时把“变慢”转化为“额外负载”。设客户端 deadline 为 D、端到端 RT 为 R(λ)。过了膝点，排队使 R(λ) 显著上升；一旦 R(λ) > D，客户端可能主动断连、重建连接并重新发送同一请求。经典 MySQL 协议以命令—响应往返驱动连接，传统线程池只限制执行线程数，并不天然持续观测排队连接的 socket：任务可能直到被 worker 取出后才读到 EOF/RST；尤其在命令已经读入的执行路径上，往往要到结果写回时才通过 my_net_write()/net_flush() 感知连接不可用，此前的 optimize、锁等待与 execute 已成为无效功。重建连接还引入握手、认证、THD/协程建立及旧连接清理成本，因此重连重试既增加请求数量，也提高每次有效请求的路径开销。

e. 提前越崖的充分条件。令 λ = λ_new + λ_retry 为原始与重试请求的总到达率，C(λ) 为服务端全部完成尝试率，S(λ) 为断连、超时或重复等不计入客户端价值的完成尝试率，则 G(λ) = C(λ) − S(λ)。对负载求导，当 S′(λ) > C′(λ) > 0 时，必有 G′(λ) < 0：完成率仍在增长，goodput 却已下降；若 C 进入平台而 S 继续增长，结论同样成立。因此客户端 goodput 的崖点可早于服务端原始执行能力的峰值，这是本文关注的提前越崖机制的局部充分条件，而非所有崖点的必要条件。无退避的立即重连重发会同步抬高 λ_retry，形成“RT 上升 → 超时/断连 → 无效执行与重连重试 → 队列更深 → RT 进一步上升”的正反馈；有退避和抖动可推迟并削弱重试同步，却只能控制新增负载，不能消除原请求已经产生的无效执行。这正是重试驱动的工作放大与亚稳态失效研究所描述的持续机制 [42][44]。崖点与亚稳态并不等价：前者是负载曲线上的持续下降，后者是触发撤除后仍维持低 goodput；本文以容量扫描识别前者，以撤载后的重试残留、恢复阈值与迟滞识别后者。

为统一上述失效模式的度量，借鉴拥塞控制的容量曲线 [40]，令 λ 为 offered load、G(λ) 为 goodput。低负载线性区有 G(λ) ≈ ηλ；膝点（knee）是曲线开始持续偏离该线性段、边际吞吐收益显著下降且 RT 增长明显加快的点，此后仍可经历一段次线性增长或近似平台，而不是立即下降；崖点（cliff）是 goodput 由此进入持续、显著下降段的点，通常伴随排队、超时与重试的急剧放大。膝点刻画容量开始饱和，崖点刻画过载开始崩塌，二者不可混用。

2.3 主流线程池为何不是完整答案

面对上述 a–e 类失效模式，线程池通常是应对突发流量的标准答案：它解耦连接与执行线程，复用线程栈，限制短语句并发，减少线程创建、上下文切换和缓存扰动，并将无限并发转化为显式排队 [37][45]。这些收益真实且必要。但线程池约束的是执行实体的数量与生命周期，并不自动获得事务依赖、锁等待图、客户端 deadline 或 OS 可运行状态。因此，更准确的问题不是“是否需要线程池”，而是“线程池能看到什么、依据什么扩容、又让谁获得 CPU”。主流实现的能力边界并不相同。

实现并发控制与优先级仍然存在的边界

机制边界一（对应 a）：依赖失明导致队列内和 OS 内双重优先级反转。MySQL 的高低队列主要依据事务是否已经开始，而不是 waiter→holder 等待边。普通 worker 可能全部阻塞在行锁上，而持有锁的事务仍在队列中等待 credit；即使 holder 已占用 worker，也可能被无关 CPU 任务抢占，数据库队列无法约束内核。Percona 文档明确描述了等待线程不占 oversubscribe、线程数逼近上限且持锁事务无法被取出的死锁路径 [46]。CockroachDB 专门提高持锁事务的 admission 优先级，恰好说明仅靠固定池与 FIFO/事务队列不足以消除反转 [47]。因此，线程池可以限制“同时执行多少”，却不能天然决定“哪一个必须先执行以释放系统关键路径”。

机制边界二（对应 b/c）：配置数、存活数、忙碌数与可运行数被混为一谈。至少需要区分 N_cfg（组数、每组目标或上限）、N_alive（已创建且尚未退出的线程）、N_busy（正在处理语句的线程）与 N_run（OS runnable 线程）。动态池按需创建和回收线程，N_alive < N_cfg 本身不是 bug，因为 max 往往不是常驻目标；但若把配置上限当成 CPU 并发保证，就会误判容量。更关键的是，N_busy 还可能包含锁/IO 阻塞、未上报等待以及被 OS 抢占的线程，N_run 才能直接解释 CPU 是否为空转。MySQL 文档明确指出，未被回调插桩的阻塞要等待 stall 时间后才能触发新线程；MariaDB 进一步列出 page fault 等无法通知线程池的等待会造成 CPU 欠利用 [45][46]。于是可能出现“组内队列非空、配置尚未到顶、busy 看似很高，但 CPU 实际空闲”的扩容滞后。

本仓库的实现也展示了这种计数语义：plugin/thread_pool/src/thread_pool.cc 中，threads_active 通过事件增减，max_active_threads = threads_user_request + stalled_threads 由 stall 检查更新，is_credit_available() 再依据这些计数决定是否放行。该设计具有明确的工程目的——避免未上报的长等待永久堵死一个组——但它是基于事件与周期的最终一致视图，不是逐时刻的 OS 调度视图。类似地，Threadpool_threads − Threadpool_idle_threads 可以表示请求处理忙闲，却不能直接当成 runnable；本论文观测到“队列为空仍有 worker 等待 100–500µs”正是 OS 抢占造成的另一层计数盲区。

机制边界三（对应 b/c）：静态尺寸和连接分组无法适应负载成本变化。请求速率并不能完整描述负载，服务时间、锁等待比例和 IO 阻塞比例同样决定所需线程数 [49]。按连接 round-robin 分组只保证数量近似均匀，不能保证 CPU 成本、热点行或事务依赖均匀，因而可出现热组排队而其他组空闲。listener 兼作 worker 时还会暂时失去监听能力，直到新 listener 被创建。TiKV 的调优文档则显示，扩大一个阶段的池会增加其他阶段的 CPU 与日志/IO 压力，瓶颈会迁移而不是消失 [48]。这意味着“CPU 核数乘以一个固定系数”只能是起始经验值，不可能同时适配干净点查、长事务、锁风暴和突发重连。

机制边界四（对应 d/e）：线程池限制执行并发，却不天然提供过载语义。固定池把突发流量转化为排队后，仍需要决定按什么信号准入、过期工作何时取消、客户端重连重试如何约束。否则，线程数配置得再精确，也只是更快地消耗有效与无效工作。PgBouncer 证明连接复用本身很有价值，但代理池既不代表数据库内执行调度，也可能牺牲会话语义 [48]；Bouncer 则进一步说明，以响应时间目标驱动的早期准入与队列控制是独立于线程数调优的一层 [50]。

因此，本文的立场是保留线程池作为高效执行底座，但拒绝把它当作完整的韧性方案。对应地，HP/VIP、COMMIT 早行与锁等待边处理 a 的活性与优先级反转；固定池、唤醒纪律、queue-time 准入和 EEVDF-Sem 共同治理 b/c 的并发开销与容量失控；前台 reactor 的断连早弃、Q2/Q3 取消和客户端/中间件退避治理 d/e 的无效执行与重试放大。固定池只负责其最擅长的执行复用，其他层分别补齐依赖语义、可观测状态、准入取消与内核调度。

2.4 设计目标：性能韧性

膝点与崖点均为配置相关的测量量；本文未加限定的“越崖”指越过基线配置的崖点。为避免凭肉眼选点，实验分别对 G 与 RT 做分段线性回归，以 G 持续偏离线性且 RT 斜率显著上升共同识别膝点，以连续至少三个负载档的 goodput 均较此前峰值下降超过 10% 识别崖点，并在运行前冻结拟合窗口与阈值；扫描范围内未出现崖点时记为 λ_cliff > λ_max 的下界，不得把最大测点伪装成崖点。据此，本文将性能韧性（performance resilience）定义为四个可测量属性的合取：

  • R1 容量韧性：膝点与崖点尽量推远，扩大线性区和可持续平台区；
  • R2 基线越崖行为：在基线崖点及更高负载下，目标配置不进入持续下降段，且无活性故障、无重试放大；若目标自身最终出现崖点，单独报告其位置与后续平台；
  • R3 恢复韧性：触发撤除后，重试残留与排队及时消散；以 RTO（恢复时间目标）度量从撤载到 p99/p999 恢复至基线 1.2× 并持续一个观测窗口的时间，目标为秒级，未恢复记为 RTO = +∞，而非“恢复较慢”；同时报告恢复负载阈值与迟滞；
  • R4 干扰韧性：比较外部干扰前后的 p99/p999 与完整 RT CDF，要求尾延迟右移和劣化倍数有界，不以 max 或单一均值替代尾部。

约束条件为：C1 免标注（默认配置不依赖任何业务优先级输入）；C2 公平有界（任何微调不得造成可观测的饿死）；C3 干净开销小（无干扰低争用下吞吐代价 ≤5%）；C4 可降级（内核不支持 sched_ext 时用户态机制独立有效）。

峰值吞吐在本框架中是回归约束而非优化目标：打榜负载仅用于确认无退化，与 Snowflake 所批评的“为基准特调”划清界限 [24]。

3 系统概述

3.1 分层架构

EEVDF-Sem 部署于 MySQL 9.7 的分层架构中（图 4）：

  1. 前台 reactor 组：reactor 线程数可配置（默认 1），每个 reactor 一个独立 epoll 实例，连接按 fd 哈希分片到各 reactor；每连接一个 C++20 无栈协程，承载连接与命令读等待；收包后在 reactor 上同步完成 parse（纯 CPU、有界、不触碰 MDL/TABLE），输出语句类型、访问表集合与事务边界供调度决策，解析失败直接返回错误、不占 worker；排队期间继续感知断连【v4】，optimize/execute 仍由 worker 执行。
  2. 执行池：worker 数可配置的线程池（配置后固定，默认 4× 硬件并发数），以整个 THD 为交接单元；高优先级队列与 VIP worker 保证排队层活性。
  3. 准入层（本设计新增）：位于 reactor 与执行池之间，按排队时间发放 credit。
  4. EEVDF-Sem 调度器：sched_ext BPF 程序，单池虚拟时间调度，消费用户态发布的意图。
  5. 意图通道：BPF maps 承载 job 类型、等待边与继承元数据；无 sched_ext 时该通道关闭，其余各层独立运行。

3.2 为什么需要前台 reactor

前台 reactor 不是简单替换网络 API，而是在 worker 之前建立一个执行前控制点：在消耗执行槽位、获取锁和产生事务副作用之前，系统第一次同时掌握请求内容、连接状态与排队状态。其必要性来自三个相互强化、但可独立成立的原因。

  1. 调度所需的语句语义只有 parse 后才存在。socket 可读只说明字节到达，不能区分普通 SELECT、COMMIT/ROLLBACK 或锁持有者的下一条重型查询；仅知道“这是 holder”而不知“它要做什么”，就只能笼统提权下一条语句，重新打开 §4.2 所述的博弈缝隙。reactor 在 Q2/Q3 之前完成 parse，并将语句类型、事务边界与该 THD 的锁持有状态联合为调度输入，才能决定进入 Normal 还是 HP/VIP、是否值得提权以及是否释放资源。若直到 worker 取任务后才 parse，排队与提权决策已经发生，语义便失去前置价值。
  2. 断连取消必须发生在 worker 执行之前。经典 MySQL 协议是请求—响应式的 ping-pong：一条连接上的命令与其 OK/ERR/结果集响应串行交替，一个显式事务又由 BEGIN、DML、COMMIT 等多轮组成 [38]。客户端通常在每轮等待上设置 deadline；过载时，响应前的排队时间可能单独超过该 deadline。默认 one-thread-per-connection 在 do_command() 内依次完成阻塞读包、dispatch、parse/execute 和结果写回（sql/sql_parse.cc、sql-common/net_serv.cc），线程池改变的是语句由哪个 worker 执行，而不是这条生命周期 [37][38]。任务排队时若无人读取其 fd，FIN/RST 不会自动转化为队列取消；若命令尚未读入，往往要到 worker 取任务后的读包才发现断连，若命令已读入，则可能到 my_net_write()/net_flush() 返回错误时才发现，之前的 optimize、锁等待与执行已成为无效功。前台 reactor 持续掌握 fd，可将 EOF/RST 对应的可读/HUP/ERR 事件转成连接代次失效，在提交前和出队后、真正执行前各检查一次，安全丢弃尚未开始的旧命令【v4】。
  3. 网络等待与查询执行具有不同的最佳并发粒度。Reactor 模式原本就针对 thread-per-connection 的上下文切换、同步与数据移动开销 [35]；SEDA 进一步证明事件驱动阶段与有界线程池可以组合，在巨大负载变化下保持高吞吐与受控退化 [36]。在本系统的目标区间——大量长连接、短网络事件、频繁 ping-pong——一个 reactor 批量处理多个就绪 fd，空闲连接不对应可运行线程；fd 固定分片与连接内串行处理又减少跨核迁移、共享队列锁和缓存/TLB 扰动。MySQL 对默认线程模型与线程池的分析同样将缓存占用、上下文切换和过度并行列为主要伸缩限制 [37][38]。因此 reactor 是网络侧的最佳匹配，而非仅为少改代码的折中；但该结论以事件处理短小、有界为前提，不能外推到 optimize/execute。

取消语义的两个边界。第一，客户端“本地已经超时”不是网络事实：只有 FIN/RST、读/写错误或显式协议信号到达后才可观测；对仍在线但已静默放弃的连接，需要客户端显式传递 deadline，或由保活/超时机制判定，不能凭排队时长臆断。第二，执行前丢弃没有副作用，执行中取消则必须通过 THD::killed、存储引擎唤醒和事务清理协作完成；尤其不能把断连简单映射为强行回滚，更不能跳过已经不可中断的提交阶段。前台 reactor 保证的是尽早发现与尽早停止无效工作，不是瞬时、无条件取消。

3.3 为什么不全局采用 reactor + 协程

协程解决的是控制流的挂起与恢复，不是并发调度。把 optimize/execute 全部改成协程，并不会减少事务数量、行锁/MDL/latch 临界区或共享缓冲池状态；更多可挂起的并发实体反而可能带来更深的锁队列、更大的缓存足迹和更多等待边。若所有协程只运行在少数 reactor 上，长查询等不可抢占的 CPU 段会造成队头阻塞；若让它们运行在多核执行器上，则 Q4 的锁竞争与 Q5 的 CPU 分配问题原样存在，仍需要准入、锁持有者保护和 EEVDF-Sem。换言之，co_await 可以降低一次让出的成本，却不能决定“谁应当运行、何时运行、运行多久”。

在并发度与唤醒纪律修正后，固定线程池依然高效，而且更贴合 MySQL。有界 worker 数限制了同时进入锁系统和 OS 运行队列的实体数，cascade notify 消除惊群，HP/VIP 保证提交活性，语义发布再修正 OS 分配；操作系统线程还提供长 CPU 段所需的抢占性，并直接容纳 InnoDB、同步 IO、条件变量与插件中的阻塞调用。相反，全局协程化要求逐一改造所有潜在阻塞点，并在每次恢复时维护 current_thd/TLS、THD mem-root 生命周期、PSI 线程归属、异常与清理语义；无栈协程由编译器保存协程帧，并不会自动迁移这些线程亲和状态。其改造面覆盖服务器、存储引擎和插件，正确性风险远大于仅前移网络与 parse。

因此本文选择网络等待协程化、事务执行线程化、CPU 分配内核协同的分阶段结构，与 SEDA 将不同阶段置于不同资源控制边界的思想一致 [36]。这也是对“事件与线程谁更优”之争的具体回答：事件模型存在阻塞、调度与可编程性限制 [35][39]，固定线程并非天然低效，失控的并发度和错误的调度才是本文要消除的问题。执行侧协程化可以作为未来独立优化，但不能替代本文的调度机制，也不是获得上述收益的前提。

设计原则可概括为一句话：公平是默认，语义是微调，微调必有界。

4 设计

4.1 公平基座：单池虚拟时间模型

所有任务（前台事务、后台 purge、外部进程）位于同一公平池，权重默认全等。每个任务维护虚拟运行时 vr，eligible 任务按虚拟截止期 vd = vr + slice/weight 排序，最小者先运行。因 IO 或锁阻塞让出 CPU 的任务保留其 lag（经 clamp 限制以防信用囤积），从而在唤醒时获得自然优先——这是 EEVDF 对突发交互负载友好的根源，必须完整继承。

针对 EEVDF 已知的唤醒放置缺陷 [5]，唤醒路径采用局部性优先的直放：优先将任务放回其上次运行的 CPU（保持缓存亲和，抑制 IPC 下降）；仅当该核被占且短期无法让出时才选择其他核并直接入 local DSQ，避免周期负载均衡纠正不及造成的 bursty 扎堆。

4.2 提交早行：有界截止期奖励

依据。2PL 下行锁持有至事务结束，COMMIT 是唯一的批量释放点：它短、必然发生、受益者是全体等待者。提权 COMMIT 不偏好任何业务，仅缩短锁系统的关键路径。ROLLBACK 同理论证成立。

机制。用户态在事务提交/回滚入口写 job_type[tid] = COMMIT，出口清除。调度器对标记任务施加截止期提前，提前量记入 §4.3 统一的借还账户：COMMIT 极短，借入量与偿还量都很小，对长期份额的影响可忽略。

提权对象的窄化。仅提权 COMMIT/ROLLBACK 语句本身，不提权“锁持有者的下一条任意语句”。后者存在博弈缝隙：应用在持锁状态下执行重型查询即可借道插队。窄化后该通道无滥用空间。

优先语句谱系（推广）。优先级只授予“执行后净减少系统等待”的语句，判定三问：是否释放被等待的资源、是否有界且短、是否是活性逃生口。据此分档：

档位语句/路径释放或收益提权条件
默认优先COMMIT / ROLLBACK全部行锁总是
默认优先XA COMMIT / XA ROLLBACKprepared 事务的锁（2PC 决策点）总是
默认优先KILL QUERY / KILL CONNECTION管理面活性逃生口总是
默认优先死锁 victim / 锁等待超时 victim 的回滚执行行锁，解开等待环由 InnoDB 标记
条件优先UNLOCK TABLES、RELEASE_LOCK()表锁、用户级 GET_LOCK有等待者
条件优先锁持有者的下一条语句（限缩版）缩短持锁窗口有等待者，且 parse 判定为 COMMIT/短 DML；长查询不提权
可选低强度语句收尾（结果写回/清理）MDL、worker 槽位cleanup 阶段可判

反例（明确不优先）：BEGIN（无释放）；SAVEPOINT/ROLLBACK TO SAVEPOINT（InnoDB 不释放行锁，无释放收益）；普通 SELECT/DML（仅经持有者继承获益）；FLUSH TABLES WITH READ LOCK 等获取全局锁的语句（应避免插队加剧 MDL 堆积）。THD 状态感知输入包括：语句类型（reactor parse）、autocommit/显式事务、持有锁等待计数、语句阶段、死锁/超时 victim 标记、XA prepared、空闲时长。全部优先走同一借还账户。

边界。当提交路径瓶颈在 IO（同步 fsync）时，该微调无收益亦无害；应用不发出 COMMIT 时无调度可救，此属应用层活性责任。

4.3 锁持有者条件性优先级继承与借还记账

依据。latch 临界区为 ns–µs 级，锁释放路径为 ms 级；持有者被抢占的每一微秒被全部等待者继承，自旋等待者还直接浪费 CPU。UFS 的 spinlock 微实验显示，失控时该现象可致 PostgreSQL PANIC，而条件性提权后总耗时仅为无干扰基线的约 2 倍 [5]。

机制（算法 1）。等待边出现时（thd_wait_begin 或 InnoDB latch 等待事件），用户态写 blocked_by[waiter] = holder 及时间戳。调度器令持有者继承其所有等待者中最小的虚拟截止期：vd_holder = min(vd_holder, min_{w ∈ waiters} vd_w)。等待边沿依赖链传递，继承深度硬上限 D（默认 8）。等待边消失（wait_end、锁释放、teardown/KILL）即撤销；每条边带时间戳，超时未刷新由清扫路径删除。

算法 1：有界虚拟截止期继承 + 借还记账
输入：等待边集合 E = {(w, h, ts)}，任务 vd[·]、borrowed[·]、debt[·]
常量：D（继承深度上限）、B_max（窗口借入上限）、D_max（未偿还上限）
1:  等待边出现 (w, h)：若 debt[h] < D_max，为 h 开通提权窗口
2:  窗口内每次调度 h：
3:      vd[h] ← min(vd[h], min_{(w,h)∈E} vd[w])   // 继承最急等待者
4:      沿 E 传递，深度 ≤ D                       // 嵌套等待
5:      h 实际运行 t：borrowed[h] += t             // 借入记账
6:      borrowed[h] ≥ B_max ⇒ 提权失效，回到普通公平 // 借入硬顶
7:  窗口关闭（锁释放/COMMIT 完成）：
8:      debt[h] += borrowed[h]; borrowed[h] ← 0
9:  窗口外调度 h：vd_eff[h] = vd[h] + debt[h]      // 更不紧急
10:     h 因 debt 被推迟 δ：debt[h] −= δ           // 用等待偿还
11: h 阻塞/睡眠：debt 保留（不随 lag clamp 抹除）   // 防逃债
12: h 退出：debt 核销；等待边 ts 超期由清扫删除    // 有界损失

为什么必须“先借后还”而不是储蓄。cgroup CFS 带宽控制的 burst（cpu.cfs_burst_us/cpu.max.burst，Linux 5.14+ [31]）允许任务组消耗历史周期累积的未用配额：这是储蓄模型，其前提是该组曾被限流且有用剩的配额。锁/latch 持有者通常持续 runnable，不存在“用剩的配额”可存，储蓄模型对它结构性失效。因此本设计采用信用模型：提权窗口内多消耗的 CPU 记为借入，窗口关闭后转为 debt，通过推迟后续调度偿还——短窗口内允许多拿，周期级总量守恒。继承决定“窗口内多急”，借还决定“窗口后怎么还”，两者正交、可独立消融。debt 独立于 vruntime 存储且不随 lag clamp 抹除，防止持有者以睡眠逃债；debt 达到上限即禁止再借，消除持续争用下的无限优先。

与经典 PI 的关系。经典优先级继承在固定优先级空间中传递“级别”；本设计在虚拟时间空间中传递“紧迫度”，与 EEVDF 的 lag 语义天然兼容，且继承量随等待者自身状态动态变化——等待者越急，持有者越优先。借还账户进一步保证了这种传递不破坏长期公平：这是 PI 的活性收益与 EEVDF 的份额保证的组合。

latch 的发布成本控制。InnoDB latch 每秒进出百万次量级，逐次发布不可行；仅在 latch 等待发生时（sync 等待数组路径）发布等待边，与 UFS 的 wait-event 触发式上报同构，稳态零开销。

4.4 以排队时间为信号的准入控制

削减开销无法单独防止崖点，必须限制在制工作量。客户端存在 deadline 时，准入目标不是榨出最后一次服务端完成尝试，而是在膝点后 RT 快速逼近 deadline 之前收缩 credit，避免“完成率仍高、goodput 已降”的超时崖点。Breakwater 的 queue-time credit 提供控制信号 [6]，超时放弃模型与亚稳态研究则解释为何还需同时削减存量无效功 [41][42]：准入抑制未来的超时反馈，断连早弃降低当前 S。本设计的准入层采用闭环 credit 控制，与既有方案的区别在信号选择：

  • 信号为排队时间而非队列深度或线程数。原型测量表明队列深度为 0 时仍有 33% 的任务等待 100–500µs（worker 被 OS 抢占），深度信号在此类失效下完全失明。
  • 过载时对仍在等待的客户端延迟接纳而非主动拒绝。新命令在 reactor 侧排队，系统不以过载错误制造额外重试；客户端仍可能按自身 deadline 超时，这由断连早弃而非“绝不超时”的假设处理。
  • 准入等待按连接公平轮询，防止单个 Agent 连接的突发扇出挤占全部容量。租户级资源分配不在 DB 内实现，由中间件承担（§7）。
  • 准入与排队取消正交【v4】。credit 限制仍有客户端价值的在制工作量；已观测断连，或携带显式 deadline 且已过期的命令，从 Q2/Q3 移除并归还 credit，不再占用 worker。取消只作用于尚未执行的工作，执行中请求遵循 §3.2 的协作取消边界。
  • 迟滞控制：credit 乘性收缩、加性恢复，避免振荡。

4.5 非业务开销的配套削减

固定线程池杜绝 stall 驱动的线程爆炸；cascade 唤醒避免惊群；调度相关计数器按 CPU 分片消除 false sharing；廉价查询的完成回投批量化降低每命令固定交接税；所有意图写入仅在事件路径发生，稳态零成本。

5.2 协程在哪里：只协程化连接与命令读等待，不协程化执行

协程的边界：前台协程承担连接/命令读 IO 与 parse，optimize/execute 保持在线程上。parse 是纯 CPU、有界（语句长度限制）、不打开 TABLE、不触碰 MDL（表打开与 MDL 获取发生在 optimize 阶段），因此可在 reactor 上同步执行而不阻塞事件循环；多 reactor 分片使该部分 CPU 可水平扩展。THD 上下文仅在同步段内持有：store_globals → parse → restore_globals，不跨 co_await。执行侧不做全局协程化的原因与改造边界见 §3.3。

连接生命周期【已有框架 + v4 parse 前移】（coroutine_connection_handler.cc）：每个连接一个 C++20 无栈协程帧（约几百字节），主循环为 co_await wait_readable(fd) → 同步 parse（失败直接回错、不占 worker）→ submit_thd_job(do_command) → co_await CommandDone。多语句包、存储过程与 parse 异常路径回退到 worker 内完整处理。认证同样以 job 形式提交执行池（thd_prepare_connection）。等待 socket 可读的连接不占任何执行线程——这是与 one-thread-per-connection 的本质区别。

Netpoller 与断连早弃【已有事件机制 + v4 排队取消】（coroutine/src/netpoller.cc）：每个 reactor 的 epoll 实例驱动其监听 fd 与连接 fd 分片，ET + EPOLLONESHOT 避免惊群与重复事件，eventfd 用于跨线程唤醒（执行完成回投），内置定时器堆与 fd 兴趣表，单批事件上限 1024；EPOLLIN/EPOLLRDHUP/EPOLLHUP/EPOLLERR 已能唤醒读等待者。v4 在此基础上为等待准入、执行队列和 CommandDone 的连接保留独立断连订阅，以连接代次标记失效，并在 submit 与 worker 出队两个时点检查；已失效且尚未进入执行的 job 直接回收、归还 credit。检查后、真正进入执行前发生的断连转入 THD::killed 协作取消，不直接销毁仍在使用的 THD。

fd 与结果写回边界：fd 只在 reactor 线程的 teardown 关闭；其他线程的 vio_shutdown() 经 pre-close 钩子转为带 token 校验的强制取消，fd 关闭前不复用，消除误 cancel/误 close 新连接的串扰【已有】。【已有】路径中，do_command() 内的结果写回仍由 worker 同步完成，因此本文不声称“所有网络 IO 已协程化”；将结果发送迁回 reactor 需要另行处理部分写、大包背压与写缓冲生命周期，不应计入断连早弃机制的待验证收益。

CommandDone 同步【已有】：双阶段协议（cmd_mu mutex + cmd_done atomic + cmd_waiting handle）。执行线程完成 job 后先置 cmd_done 再经 eventfd 通知 reactor；协程侧 await_ready 快路径在作业已完成时直接返回不挂起，慢路径注册 handle 挂起。该协议保证“完成信号不丢失、协程不永久悬挂”，是每命令两次线程切换的固定成本所在。

THD 移交【已有】：交接单元是整个 THD 对象而非执行计划——AccessPath 内嵌大量指向 THD main_mem_root 的指针，不可序列化。worker 接管时执行 store_globals() + thd_set_thread_stack()，释放时 restore_globals()。这是 MySQL 上游已有的跨线程迁移机制，本架构只是复用。

5.3 线程池在哪里：固定执行池 + HP/VIP 活性通道

执行池【已有】（coroutine/src/executor.cc）为 pthread 池，worker 数可配置（默认 max(4 × hardware_concurrency, 16)），VIP worker 数可配置（默认 1，worker 0..num_vip-1 只消费 HP 队列），创建时 sched_setaffinity 绑核并执行 my_thread_init/end。默认系数 4 用于吸收 do_command 内的行锁等待与同步 IO 原地阻塞——阻塞留给线程，不挂起归还（v1 的明确取舍；执行侧挂起列为远期工作）。固定池从根本上消除了 MySQL Thread Pool 插件 stall 驱动的线程爆炸（其上限可达 65536 线程）。

唤醒策略为 cascade notify：submit() 时 notify_one；worker 取任务时若队列剩余 >1 则再 notify_one。纯 notify_one 会让单 worker 独占突发队列并在阻塞 IO 后死锁（实测 32 连接 0 TPS）；notify_all 造成每秒 25 万次上下文切换（实测 311 TPS）；cascade 修复后 3176 TPS。

HP/VIP 通道【已有 v2】：reactor 提交前查 is_lock_holder(thd)（THD 级等待图，等待计数 >0 即命中），命中则提交 HP 队列；0 号 worker 为 VIP 专用 worker，只消费 HP 队列。即使普通 worker 全部阻塞在行锁上，持锁者的 COMMIT 仍有线程执行——执行池活性死锁在排队层被结构性消除。该机制纯用户态、始终编译，不依赖 sched_ext。

5.5 调度怎么实现：EEVDF-Sem 的 BPF 实现

调度器为 sched_ext struct_ops BPF 程序【v4，替代 v3 的三层 DSQ 实现】，由用户态加载器在运行时载入，不修改内核源码。

回调分工：

  • enqueue（任务变 runnable）：从 per-task map 读取 vr/debt/job_type，计算 vd = vr + slice/weight + debt − bonus(job_type)；若处于提权窗口则再执行 vd 继承（取等待者最小 vd，深度 ≤8）。普通任务入共享 DSQ（按 vd 排序）；唤醒直放场景下直接入目标 CPU 的 local DSQ
  • dispatch（CPU 空闲取任务）：从共享 DSQ 取 vd 最小者派发；被推迟的任务按推迟时长冲减 debt（偿还路径）
  • select_cpu（唤醒选核）：局部性优先——首选上次运行的核（缓存亲和）；仅当该核被占且短期无法让出时改选他核。已知的实现陷阱：此回调直插 SCX_DSQ_LOCAL 会跳过 enqueue，微调与记账逻辑必须在该快路径上有等价实现或显式禁用，否则提权静默失效
  • running/stopping：实际 CPU 消耗记账——vruntime 正常推进；提权窗口内的运行时间累加 borrowed，达 B_max 关闭窗口

per-task 状态【v4】（BPF map，key = tid）：vr、debt、borrowed、job_type、提权窗口时间戳。等待边单独存于 blocked_by map（key = waiter tid，value = holder tid + ts）。debt 独立于 vr，不经过 lag clamp——阻塞/睡眠不清债；任务退出时 map 条目由 teardown 路径删除（forget_thd），残余 debt 核销。

发布纪律【已有，v2/v3 工程教训固化】：执行 job 开始/结束（thread_job_begin/end）解决显式事务 holder 语句间隙 real_id = 0 的 tid 归属；所有 BPF map 写入必须在释放等待图叶子锁（s_wait_mu）之后进行——v2 曾因锁内发布导致自死锁，首次行锁等待即全服挂死；KILL/回滚/teardown 的清理路径是正确性测试必查项。

性能预算：意图写入仅发生在事件路径（job 边界、锁等待、COMMIT 进出），稳态无写；对标 UFS 的 hinting 开销实测 ≤1%，本设计 v3 已测得干净负载约 5% 总开销（含 BPF 回调），v4 预算不高于该水平。

6.1 研究问题

  • RQ1（干扰韧性）：外部 CPU 干扰下，语义发布能否约束尾延迟劣化？
  • RQ2（锁活性）：等待者数超过执行线程数时，持有者 COMMIT 是否仍被调度执行？

  • RQ4（容量曲线与恢复，v4 目标）：准入控制能否推远膝点和崖点、在基线越崖后保持有界 goodput，并缩短负载回落后的恢复时间？

6.2 实验设置

【实测】v1–v3 数据来自两类环境：（a）本地 aarch64 10 核、Linux 6.18.15、NVMe；（b）阿里云 ecs.c9i.4xlarge 16 vCPU，数据库与压测节点分离，sysbench 1.0.20，32 表 × 10 万行，open-loop 点查与封闭环读写混合。对照配置：C1 = one-thread-per-connection（OS-only 基线）、C2 = 协程执行池无 SCX、C4 = 协程 + sched_ext 语义发布。每配置 ≥2 轮取中位数，噪声注入于数据库节点。

6.3 测量方法学

开放环与封闭环分工。封闭环（固定客户端线程数，完成一个再发下一个）适合可重复地比较吞吐，但存在 coordinated omission：服务变慢时客户端自动少发请求，尾部被“测没”[32][33]。因此过载、突发、尾延迟类实验一律采用开放环（按预定到达过程发送，速率不随响应变慢而降低），封闭环仅用于正向回归基线。

指标口径。分列原始到达率 λ_new、重试率 λ_retry、总 offered rate λ = λ_new + λ_retry、服务端完成尝试率 C、无效完成率 S 与 goodput G = C − S（在客户端 deadline 前完成且结果被有效接收、不计入 abort/重试的吞吐）。断连、超时或重复等完成尝试均计入 S，不能把“服务器做了事”误记为客户端价值；同时报告 S/C、重试放大系数 λ/λ_new、重连/认证速率、C 的峰值位置与 G 的崖点位置，以检验二者是否分离。RT 报告 p50/p95/p99/p999/max 与 SLO 违约率，不用均值替代尾部。每配置 ≥2 轮取中位数，max 离群必须复测确认。

观测分解。结果（C、S、G、断连前后取消数）、排队（handoff 深度、submit→run 直方图、OS run queue）、依赖（row lock waits/time、deadlocks、HP submitted/executed、map 条目）、资源（上下文切换、迁移、IPC、RSS/FD、重连与认证开销）。submit→run 混合用户态排队与 OS 调度等待，不单独归因于任何一层。

客户端重试模型。开放环客户端为每个逻辑请求设置 deadline 和 request ID，超时后主动关闭连接、重建并重新发送同一请求，以便识别旧连接无效执行与跨连接重复完成。至少比较三组：（a）不重试；（b）立即重连重发，无退避；（c）指数退避加全抖动后重连重发。deadline、退避初值/上限和最大重试次数在运行前冻结；三组使用相同的原始到达过程，分别记录实际 λ_retry，不能用封闭环客户端自带的背压代替重试模型。测量时区分单次尝试超时与逻辑请求总 deadline，退避等待计入端到端 RT，不得通过每次重试重置计时器来隐藏总延迟。

对照与消融。C0 = 原生 Thread Pool、C1 = one-thread-per-connection、C2 = 协程执行池无 SCX、C4 = EEVDF-Sem。逐项消融：COMMIT 奖励开/关、vd 继承开/关、借还开/关、准入开/关；针对 RQ6 再比较 reactor parse 开/关、断连早弃开/关，并报告 reactor 数量与每命令交接成本。全局执行协程化没有实现，不作为未经验证的性能对照。噪声注入必须在数据库节点；每配置独立输出目录；远程状态采集失败不得静默归零。

6.8 执行规范

噪声必须注入数据库节点（早期误注压测节点导致实验无效）；每配置独立输出目录；≥2 轮中位数并检查 max 离群（单次 217 ms 离群经复测排除）；远程状态采集失败不得静默归零；封闭环与开放环数字不混用。原始 offered rate 与包含重试后的实际到达率分列，不重试/立即重试/退避重试不得共用结果目录；RT 以客户端 request ID 测量，C/S/G 由客户端与服务端记录对齐，避免将重连后的成功、旧连接迟到响应和重复执行重复计数。

7 讨论

为什么不做自动负载分类？IconqSched [29]、LSched [22] 证明了预测式调度的潜力，但其前提是负载可标注或可预测。本设计刻意将智能限制在结构语义内：COMMIT 与锁等待边是确定事实，无模型误差、无训练成本、无回退负担。

为什么不做库内业务优先级？resource group、租户权重等机制把高频变化的业务语义固化进最难变更的组件，且只能控制线程级 nice/绑核，无法覆盖锁、缓冲池、IO 与内存带宽，既不完整也不可持续。本设计将业务间资源分配整体上移中间件：泳道隔离、租户配额、限流与重试退避由最了解租户与 SLO 的一层执行；数据库只对自身效率负责——结构语义微调、全局 queue-time 准入（业务无关的自我保护）与按连接公平排队，并向中间件暴露 queue-time、goodput、准入延迟等闭环信号。需要强隔离的租户，推荐泳道级独立实例而非库内权重。

与 PreemptDB 的分工。PreemptDB [13] 在数据库层用用户态中断实现事务级抢占，适合需要事务内精细抢占的场景；本设计在 OS 层工作，任务阻塞即让出 CPU、可同核并发多个高优任务，且不依赖特定硬件特性。两者解决的是不同粒度的抢占问题，可组合。

局限。本设计不解决 IO 瓶颈、应用不发 COMMIT、NUMA 分区与 AP 内部算子级并行；sched_ext 无稳定 ABI 承诺，需锁定内核版本。reactor 支持可配置多分片（默认 1）以缓解极高 QPS 下的单点，但 parse 仍须有 CPU 时间预算，不能把超大或异常复杂语句的长期占用隐藏在“有界”二字之后。断连早弃只覆盖可观测的 FIN/RST/错误或显式 deadline，不能凭空发现网络黑洞；执行后断连也不保证立即终止。结果写回当前仍可能阻塞 worker，网络侧最优结论不覆盖尚未协程化的大结果集发送。

8 相关工作

数据库调度与优先级。Carey 等 [8] 早已指出 DBMS 优先级需跨 CPU、磁盘与缓冲协同；CATS [25] 以阻塞面加权决定锁授予顺序，与本设计的 CPU 侧继承互补；R-SMF [9] 与 DRFT [10] 分别探索事务排序空间与多租户事务公平；Polaris [23]、Natto [20] 在 OCC/分布式语境下实现事务优先级。PreemptDB [13] 提供事务级用户态抢占。与上述工作不同，本文聚焦免标注的结构语义与内核 CPU 分配。

事件驱动、线程与混合服务器。Reactor [35] 给出同步事件分派的基本结构及其非抢占、不可阻塞约束；SEDA [36] 用显式队列连接事件驱动阶段和有界线程池，证明混合架构可同时获得高并发与过载退化能力。von Behren 等 [39] 则从可编程性与调度角度反驳“所有高并发服务都应事件化”。MySQL 默认连接模型和 Enterprise Thread Pool 的分析 [37][38] 进一步表明，减少连接线程数有价值，但并不替代事务并发控制。本文据此只把 reactor 放在 Q1 与执行前语义边界，把 Q2–Q5 分别交给准入、固定执行池、锁系统与 OS 调度器，而不是重述“事件优于线程”的一般性结论。

线程池、动态调参与准入。MySQL Enterprise Thread Pool 以分组、stall 扩容和事务队列控制短语句并发 [45]；MariaDB/Percona 暴露未感知等待、oversubscription 与锁依赖死锁问题 [46]。TiKV 采用多阶段专用池 [48]，CockroachDB 则以动态 slot、runnable/调度延迟和持锁事务提权实现准入 [47]，说明线程池正从静态尺寸走向信号驱动，但也证明仅靠池无法终结调度问题。Bahadur 等指出仅用请求率调容不足，还需考虑服务时间 [49]；Bouncer 将准入推进到响应时间目标与早期拒绝 [50]。PgBouncer 位于连接代理层并附带会话限制 [48]。与这些工作不同，本文不另造一个池尺寸算法，而是区分配置、存活、busy 与 runnable，并将锁依赖、排队时间和客户端超时语义接入固定执行池与 OS 调度器。

OS 调度与干扰治理。IX [4]、Shinjuku [17]、Caladan [11] 等量化并治理微秒级调度开销与干扰；Breakwater [6] 以排队时间驱动 credit 准入，本文将其信号机制适配到数据库执行池。Jain 的膝点/崖点容量模型 [40] 为本文区分“饱和后增长放缓”与“过载后持续崩塌”提供术语基础，本文进一步将其落实为数据库 goodput 的可测判据。cgroup CFS 带宽 burst [31] 提供储蓄型配额借还，本文针对持续 runnable 的锁持有者改造为信用型借还。EEVDF 的唤醒放置缺陷在 [5] 及内核社区多次报告中均有记载。

超时放弃、重试放大与取消。Mathur 和 Apte [41] 在 listener/worker 两阶段共享 CPU 模型中指出，超时放弃后的无效处理会使 goodput 在资源持续满 utilization 时显著下降，为本文区分 C 与 G 提供直接依据。Bronson 等 [42] 将数据库后端重试归纳为工作放大和亚稳态失效，Huang 等 [44] 进一步证明此类失效在真实事故中反复出现；本文补充 MySQL 特有的已读命令执行至结果写回才感知断连、重连认证成本，以及 S′ > C′ > 0 的提前越崖判据。Dean 和 Barroso [43] 的 hedged/tied requests 表明及时取消能约束重复工作，本文将这一原则落实到 reactor 的执行前断连早弃，但保留事务执行中的协作取消边界。退避与重试预算属于客户端/中间件反馈控制，不能替代数据库侧的准入与存量无效功消除。

DB–OS 协同。Practical DB-OS Co-Design [27] 采用特权内核 bypass；Tigger [7] 与 BPF-DB [26b] 用 eBPF 下沉数据库逻辑；MosaicDB [14] 以协程化事务隐藏 OS 调度延迟。UFS [5] 与本文最为接近：本文保留其意图通道与条件性提权，去除其人工 TS/BG 分层，并将基座替换为单池 EEVDF 虚拟时间模型，新增过载准入与突发韧性目标。

性能剖析。Looking Glass 系列 [12, 28]、DBx1000 [26]、Shore-MT [18]、微架构分析 [19] 共同构成本文开销归因的证据链：瓶颈从锁与缓冲池上移至通信、内存层次与调度协同。

9 结论

本文主张将数据库高并发调度的目标从峰值吞吐转向性能韧性，并给出一条无需业务标注的技术路线：前台 reactor 将连接多路复用、断连感知与 parse 置于执行之前，固定执行池保留 MySQL 的同步语义；在此混合边界上，以 EEVDF 公平虚拟时间为基座，用两类普适结构语义（提交早行、锁持有者条件性继承）做有界微调，以先借后还的记账保证周期级公平，配合排队时间准入与失效工作早弃应对 Agent 时代的突发、过载和客户端超时。协程只用于最有收益的网络等待，不被当作锁管理或 CPU 调度的替代品。同时，G = C − S 模型将客户端超时导致的无效完成纳入容量分析，解释 goodput 为何可先于服务端完成率峰值越崖，并以有/无退避对照和撤载迟滞区分暂时过载与亚稳态。分阶段原型的实测证据表明，语义发布在外部干扰下将尾延迟劣化从 7.6 倍降至 1.4–1.7 倍，代价约为 5% 干净吞吐；断连早弃的收益仍属 v4 待验证设计。完整韧性评估（膝点/崖点、恢复时间、突发吸收与前台取消）是下一步工作。
